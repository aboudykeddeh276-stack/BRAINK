# KEX/BRAINK Capability Resolver Policy — Global Infrastructure Progression

For infrastructure/online/distributed-system work, BRAINK must discover existing engineering before deriving new architecture.

```text
USER INTENT
→ CAPABILITY DISCOVERY
→ EXISTING KEX SKILLS / MODULES / EVIDENCE
→ REUSE | BRIDGE | ADAPT | DERIVE | UNKNOWN
→ IDENTIFY NEXT GLOBAL DEPENDENCY
→ EXECUTE / BIND AT THE RELEVANT EXTERNAL BOUNDARY
→ INDEPENDENT READBACK
→ KEX STATE/ROUTE COMMIT
```

## Local admissibility rule
Local conformance is inherent to an admissible KEX component. It is not the objective of the online/distributed transition and is rerun only for regression, changed internal invariants, or specific diagnostic need.

## Global-first rule
The active progression begins with `ONLINE_GLOBAL_BINDING`, then advances through IoT, Web3, Web4, cloud carrier-independence and mesh closure according to material dependencies.

A capability already present in the authoritative skill/package topology must not become functionally unavailable merely because the current branch or conversation did not mention it recently.

## Resolver order
1. inspect existing capability and prior evidence;
2. preserve established internal admissibility unless changed evidence invalidates it;
3. identify the next unresolved global predicate;
4. reuse directly if equivalent;
5. adapt/bridge if interfaces differ;
6. derive only missing mechanics;
7. obtain boundary-appropriate external observation/readback;
8. preserve prior engineering and negative knowledge.

## Logical integration rule
A logical KEX edge is the default integration mechanism. Repository/source-tree merging is not the default. Codebases retain independent source lineage unless an independently established build/runtime dependency requires physical unification.
