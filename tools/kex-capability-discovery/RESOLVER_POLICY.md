# KEX/BRAINK Capability Resolver Policy — Canonical Runtime and Global Progression

For infrastructure, online and distributed-system work, BRAINK must discover existing engineering before deriving new architecture.

```text
USER INTENT
→ CAPABILITY DISCOVERY
→ CANONICAL KEX RUNTIME
   → SERVICE GRAPH RESOLUTION
   → HARDWARE CONTRACT CLOSURE
   → CARRIER_READY VIRTUAL MACHINE
   → REHYDRATION / PLACEMENT RESOLUTION
→ EXISTING SKILL / ADAPTER / EXTERNAL AUTHORITY
→ EXTERNAL ACTUATION ONLY WHERE REQUIRED
→ INDEPENDENT READBACK
→ KEX STATE/ROUTE COMMIT
→ RECOMPUTE NEXT GLOBAL DEPENDENCY
```

## Canonical runtime

`tools/kex-runtime/runtime.mjs` is the canonical execution spine. Earlier service-mesh and virtual-hardware files are retained as lineage evidence and experiments, but capability resolution must prefer runtime v2.

## Local admissibility rule

Local/internal conformance is inherent to an admitted KEX component. It is not an online/distributed promotion state. Internal tests are rerun for regression, changed invariants or targeted diagnostics, not as a substitute for external progress.

## Machine-carrier rule

A derived virtual machine is not a carrier merely because a descriptor exists. The required hardware families must close first. Only `CARRIER_READY` machine coordinates may derive child machine spaces or receive rehydrated workload state.

## Failover rule

Failover is rehydration of preserved KEX lineage. The runtime selects randomly over the current admissible hardware-complete carrier population, records the entropy observation in the transition route, and does not require primary/secondary or failback semantics.

## Global-first rule

The externally actionable progression remains:

```text
ONLINE_GLOBAL_BINDING
→ IOT_GLOBAL_DEVICE_SPACE
→ WEB3_DISTRIBUTED_STATE_SPACE
→ WEB4_SEMANTIC_EXECUTION_SPACE
→ CLOUD_CARRIER_INDEPENDENCE
→ MESH_GLOBAL_CLOSURE
```

This is a dependency graph, not a stage counter. A higher label is never promoted without its actual external predicates.

## Resolver order

1. inspect existing capability and prior evidence;
2. resolve existing virtual service relationships;
3. resolve an existing or derivable `CARRIER_READY` machine before allocating new physical infrastructure;
4. reuse directly if equivalent;
5. create a typed logical bridge if interfaces are compatible;
6. create an explicit tested adapter if representation differs;
7. derive only genuinely missing mechanics;
8. materialise through QEMU/KVM/HVF/cloud/bare-metal/BIND/FRR/API or other typed external adapter only when required;
9. obtain boundary-appropriate external observation/readback;
10. append the transition and recompute unresolved dependencies.

## Logical integration rule

A logical KEX edge is the default integration mechanism. Repository/source-tree merging is not. Codebases retain independent source lineage unless a genuine build/runtime dependency independently requires physical unification.

## Claim boundary

Virtual service closure, machine closure and rehydration are software/runtime state. They do not by themselves prove WAN deployment, registrar authority, authoritative DNS publication, TLS identity, BGP advertisement, public API execution, cloud materialisation or physical bare-metal performance.
